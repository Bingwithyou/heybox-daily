# 登录人机验证

2026-10-27，用户批准在现有登录流程中接入小黑盒要求的人工验证码，并继续真实登录与耗时验收。沿用当前网站、VPS 和发布授权；不新增远程资源。

## 已核实的问题

小黑盒发码接口返回 HTTP 200、业务状态 `show_captcha`、提示“请先验证”，`result` 含 `appid`。优化路径和仅恢复旧 native preflight 的路径均返回同一状态；本次对照耗时分别为 10.285 秒、14.133 秒。手机重新登录后，现有网站会话、托管凭据的任务及签到状态查询仍成功。不能据此保证凭据永久有效，也不能断言上游风控的具体触发规则。

APP 1.3.398 的正常流程加载腾讯 `TCaptcha.js`，以本次 `appid` 展示验证码。回调 `ret=0` 后，将 `captcha_type=confirm`、`ticket`、`randstr` 放入原接口的 query，再提交原手机号、设备及请求 body。前端回调不等于服务端认可；只有小黑盒最终 `status=ok` 才允许继续。

## 批准的行为

- 仅在小黑盒要求时显示“完成人机验证”，按需加载腾讯官方 SDK。正常不触发验证的登录保持原流程。
- 网站使用官方 2.0 `TJCaptcha.js`。初次真实验收发现旧版 iframe 模板在受控 Chrome 中停于 `about:blank` 并返回 `1007`；同一浏览器的最小对照验证了 2.0 可以显示挑战。按官方兼容升级说明只更换 SDK 地址，后端票据合同不变，真实账号验收仍须单独完成。
- 执行端在内存保留原手机号、Config、浏览器 binding 和当前阶段，挑战 5 分钟后销毁。发码和验证码校验阶段都能处理 `show_captcha`。
- 浏览器只得到随机挑战 ID、到期时间、阶段和公开 appid，不得到小黑盒凭据或设备令牌。
- 人工完成后将票据交给执行端，以同一设备/手机号继续原操作。前端取消、SDK 错误、容灾回调、票据过期、重复或并发提交均不能当作成功。
- 每个挑战的验证码校验仍最多 3 次；人工验证码提交也最多 3 次。成功消费、过期和耗尽次数都会清理内存。已有托管凭据仅在新登录及身份回读成功后替换。
- 初次发码维持手机号/IP/全局限流；已存在的人工挑战继续操作走独立次数限制，不重新生成设备或无限消耗发码接口。取消不自动重发。
- 若提供方限制当前域名、appid 鉴权或 IP 组合，显示实际失败并保留旧凭据，不伪造来源、不绕过限制。真实验证码操作遵守工具要求，由用户在操作前确认。

## 数据合同

登录步骤公开返回判别状态 `sent`、`captcha` 或 `authenticated`。`captcha` 包含挑战 ID、到期时间和数字 appid；`sent` 包含挑战 ID、到期时间和重发等待时间。执行端的内部结果额外携带 Config，不能直接返回浏览器。新增受原浏览器 Cookie 绑定的 `complete-captcha` 操作，仅接收挑战 ID、ticket、randstr；完成后沿用统一的步骤结果。验证阶段需要暂存的短信验证码仅保存在该挑战的内存中。

## 压力测试与未决限制

已检查：跨浏览器借用挑战、成功重放、并发回调、取消后重试、错误验证码、挑战过期、重复票据、上游再次要求 CAPTCHA、SDK 加载失败、容灾假成功、缺失或非法 appid、执行端重启、旧凭据保留。腾讯支持域名/应用鉴权配置，小黑盒的实际配置不可见；浏览器和 VPS 的不同 IP 是否被接受，必须以真实验收为准。
