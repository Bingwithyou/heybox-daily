# 每日任务随机退避与全局启动节奏

用户已批准实现、正式部署，以及对现有待重试任务做一次打散；保留执行次数与历史。不包含 Git commit/push。

后续调整：用户要求将最大并发从 8 降至 6，保留每 4 秒一次的启动门槛；已同步线上消费者和本地配置。下文保留初版批准方案，当前并发以 `apps/executor/wrangler.jsonc` 为准。用户随后另行授权提交并推送本次改动。

## 行为

- 普通临时错误（含 HTTP 403）第 2–5 次执行分别等待 5–10、20–40、60–120、120–240 分钟；限流分别等待 15–30、30–60、60–120、120–240 分钟。
- 从本次失败结束计时，使用固定下限加均匀随机窗口（窗口等于该档下限）。有效 Retry-After 是最早时间约束，随机结果持久化，扫描和重复投递不重抽。
- 全部日常任务共享每 4 秒最多一次实际领取；包括首次、自动重试和手动重新投递。不积累空闲额度。保留 Queue 8 并发。
- 最多保留 32 个已预留投递、已投递或运行中的日常任务；其余留在 D1。按 4 秒槽位延迟投递，实际消费再次校验全局资格，避免延迟消息集中到达时突发执行。
- 等待启动不增加 attempts，不创建 job_attempts，也不占运行租约。重复和陈旧消息不推进全局时钟。
- 每天最多 5 次，不跨北京时间日期。登录失效、取消、暂停、租约与版本检查保持有效。

## 实现约束

沿用 D1 与 Queues：新增全局调度状态和 jobs.dispatch_at；D1 batch 将条件领取、全局时钟推进和尝试记录写入合为一个事务。延后消息不在消费者内 sleep；未取得资格时以队列延迟重新投递，运输层死信仍通过现有 D1 恢复路径处理，不扣业务次数。

新退避也适用于租约超时恢复。首轮调度时间仍为 00:30。启动速率是任务级限制，并不承诺上游 HTTP QPS。

## 现有任务

部署前只读保存符合条件的待重试任务快照；部署后按新窗口计算 available_at，取不早于旧 available_at 的值。只更新仍 queued、仍有效且启用、次数和 updated_at 均未变化的同日任务，取消旧投递 token，保留 attempts/result/job_attempts。对随机结果跨日的任务遵循不跨日规则。变为 running/completed/failed 或凭据状态变化的记录跳过，不恢复次数耗尽的任务。更新保存审计回执并回读。

## 风险与验收

- 4 秒是保守运行参数，不是已验证的上游安全阈值；按 1,559 账号首轮启动理论约 104 分钟，不保证完成时间。
- 并发领取只能有一个成功，失败事务不能消耗资格，重启和重复投递不能产生突发额度。
- 重试随机范围、Retry-After、跨日、第五次停止、历史保留均有回归测试。
- 并发派发不突破 32 缓冲；到达顺序变化、早到消息与死信恢复不丢任务。
- 发布后校验线上源码、资源绑定、8 并发、Cron、真实 starts 时间间隔和退避分布。

回滚代码保留新增字段和已经写入的次数/历史；不回滚任务数据，不把已延后的任务集中提前。若降级派发逻辑，保留领取侧启动限制直到积压处理完成。
